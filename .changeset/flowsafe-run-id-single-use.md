'@proofoftech/flowsafe': minor

Breaking: `FencedWorkflowsStorageD1` refuses a write whose run provenance names another start than the stored row's, by its start token, with `RunSettledConflictError` (HTTP `409`), whether or not the row is settled. Run ids are single-use: never start an id again, even after retention removed its run, because `RunnerRuntime.start` refuses an id only while its run's row exists. Before this change a leg of an earlier run still running on another instance when its id was started again wrote its snapshots over the later run's row until the leg ended, and a leg of the earlier run whose state could not be stored recorded the later run as `failed`; the leg now ends at its next write, and the later run's row stays as that run wrote it. The shipped hosts mint a new id for every start; a custom `newRunId`, which also mints thread ids, that repeats values, or a host that calls `RunnerRuntime.start` or the run object's start route with a chosen id, is affected. A write or a stored row without a start token is not refused for it: a run started without an execution fence stores its first row without one, so a leg of the earlier run can still write over that row, and the later run's own writes then answer `409`. A leg run by an earlier flowsafe version still writes over the later run.
