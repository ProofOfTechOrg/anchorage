'@proofoftech/flowsafe': patch
---

With a short `RUN_RETENTION_DAYS` such as `0`, retention no longer removes a run's terminal snapshot before the run object or agent thread object that started the run has read its outcome: `purgeExpiredWorkflowRuns` keeps a terminal snapshot while its run's `run` claim in `resourceOwnerTable` is reserved, and removes it on a later pass. Both objects also record in their start journal that they read the outcome before they commit that claim, so when retention removes the run before the journal clears, as for an unthreaded agent run that ended after suspending, or a start whose instance stopped between the commit and the clear, the object's next wake clears the journal. Before this change such a start answered `409` or `503` and its object kept the journal and woke every minute; the run's `dispatch-status` answered `503`, so a scheduled fire of the run stayed deferred, and an agent thread stayed blocked by the run. This does not repair a start journal an earlier flowsafe version wrote, which records no read: an object already in that state when the deployment upgrades stays in it, and so does one whose run retention removes before the object's first wake on this version reads the run, including a start an earlier version served during the deploy. `purgeExpiredWorkflowRuns` also no longer fails a pass that has a snapshot to remove when the configured `resourceOwnerTable` does not exist: it treats the table as holding no claim and logs one `retention-config` line per pass. A purge by an earlier flowsafe version during a deploy, or by a direct caller that passes no `resourceOwnerTable`, can still remove such a snapshot.
